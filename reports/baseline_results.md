# AdmitFlow - Primary Classification Baseline

> **The dataset is synthetic.** Every figure below was computed on data generated by
> `scripts/generate_dataset.py` from the documented AdmitFlow admission-funnel
> specification. These numbers describe the behaviour of a model fitted to a *simulated*
> funnel. They are **not** real-world institutional performance and must never be
> presented as such.

Produced by `scripts/train_baseline.py` | seed `20240817` | no hyper-parameter tuning.

---

## 1. Task definition

| Property | Value |
|---|---|
| Target | `enrolled_flag` (1 = applicant enrolled in this programme/cycle) |
| Prediction unit | one `application` |
| Prediction point | `application_submitted_ts` |
| Population | `data/processed/applications_modelling_view.csv` |
| Split | `split_hint` - deterministic function of `cycle_id` |
| Decision threshold | 0.50 |

**The base rate for this task is the modelling-view rate, not the top-of-funnel rate.**
The modelling view contains only applications that reached `application_submitted`, so the
reference rate is the *submitted* population rate (validation 0.2661,
test 0.2629). The top-of-funnel rate of 0.121 applies to
`fact_application`, a different and 2.3x larger population, and is **not** the correct
reference for any metric on this task.

## 3. Feature selection and leakage boundary

Features were taken **only** from the explicit `primary` allow-list published in
`scripts/admitflow_schema.py`. The modelling view was never auto-screened: the script
intersects the schema allow-list with the available columns. This matters because the
modelling view physically contains `stage_reached` and `stage_reached_order`, both of which
are exact deterministic restatements of `enrolled_flag` (verified: `stage_reached_order == 7`
iff `enrolled_flag == 1` on every row). A 'drop the target column and use the rest' workflow
would have produced a meaningless perfect score.

| Quantity | Count |
|---|---|
| Declared `primary` allow-list features | 45 |
| Of which present in the modelling view without a join | 43 |
| Of which recovered by join from a raw table | 2 |
| Of which held out as bookkeeping / grouping | 2 |
| **Declared features used as model inputs** | **43** |
| Design-matrix columns after one-hot encoding (fitted on train) | 124 |

One-hot encoding expands the matrix from 43 declared features (32 numeric, 11 categorical) to 124 columns. The one-hot block is fitted on the
training split only, so categories first seen at validation or test time contribute no
column: `cycle_id` yields 2 columns rather than 4 (the test cycle `CYC-2025` is unseen) and
`campaign_id` yields 16 rather than 32. `handle_unknown="ignore"` maps those unseen levels
to an all-zero block instead of raising.

**Declared features absent from the modelling view** (recovered by join, not omitted):

| Feature | Source | Join key | Recovery |
|---|---|---|---|
| `region_inquiry_weight` | `data/raw/dim_region.csv` | `region_id` | recovered, 0 nulls |
| `application_count` | `data/raw/fact_applicant.csv` | `applicant_id` | recovered, 0 nulls |

**Held-out bookkeeping fields.** `admitflow_data_contract.md` I.1 lists these inside the
`primary` allow-list under the heading *Grouping / bookkeeping*. They are safe to carry on a
row but are not predictive inputs, so they were held out of the design matrix:

| Held out | In allow-list? | Reason |
|---|---|---|
| `split_hint` | yes | deterministic function of `cycle_id`; would leak the evaluation design into the features |
| `cohort_label` | yes | strict nesting of `programme_id` and `cycle_id`, both already present; its training levels are all unseen at test time |
| `application_id` | no | surrogate key, unique per row; pure memorisation capacity. Never an allow-list member and never used as an input |
| `applicant_id` | no | surrogate key. Not an allow-list member; it is the grouping key to use if resampling is added later |

**Fields the schema classifies as POST_OUTCOME or TARGET.** None is in the design matrix.
The script asserts this programmatically and aborts with exit code 2 if any appears.
The 25 columns are listed in `admitflow_data_contract.md` I.3 and include
`stage_reached`, `stage_reached_order`, `dropoff_stage`, `dropoff_reason`,
`admission_decision_ts`, `application_verified_ts`, `doc_verification_status`,
`doc_query_raised`, `doc_query_count`, `decision_type`, `selection_score`,
`offer_letter_issued`, `offer_deadline`, `scholarship_offered`, `scholarship_amount_inr`,
`withdrawn_flag`, `withdrawn_date`, `admitted_ts`, `enrolled_ts`,
`days_submitted_to_verified`, `days_verified_to_decision`, `days_decision_to_enrolled`,
`admitted_flag`, `enrolled_given_admitted_flag`, `enrolled_flag`.

`selection_score` -- the institution's internal merit score, deliberately retained in the raw
data as a leakage trap (contract `D-11`) -- is **not present** in the modelling view and was
therefore never a candidate. The safe alternative
`is_repeat_applicant_at_prediction` **is** used; the leaking lifetime flag
`fact_applicant.is_repeat_applicant` is not.

## 4. Preprocessing and model configuration

| Stage | Configuration |
|---|---|
| Numeric | `SimpleImputer(strategy="median")` -> `StandardScaler()` |
| Categorical | `SimpleImputer(strategy="most_frequent")` -> `OneHotEncoder(handle_unknown="ignore", drop=None)` |
| Date/time features | parsed as ISO-8601, converted to whole days since `2022-01-01` |
| Assembler | `ColumnTransformer` (numeric block, categorical block, `remainder="drop"`) |
| Model | `LogisticRegression(penalty="l2", C=1.0, solver="lbfgs", max_iter=5000, random_state=20240817)` |
| Tuning | **none** - single fit, no search, no cross-validation, no threshold optimisation |
| Random seed | `20240817` (also passed to `LogisticRegression`; `lbfgs` is deterministic) |
| Converged | `n_iter_ = 80` of 5000 |
| Threshold | fixed at 0.50 |

`handle_unknown="ignore"` is required, not cosmetic: `cycle_id` and `campaign_id` levels
first appear at test time, and an unseen level maps to an all-zero block rather than raising.

### 5.3 Calibration

Calibration slope / intercept from a logistic regression of the outcome on `logit(p)`:
validation slope **0.8260**, intercept **-0.4243**;
test slope **0.9153**, intercept **-0.3271**.
A slope near 1.0 and intercept near 0.0 indicates well-calibrated probabilities.

**Reading: the model is mildly over-confident.** A slope below 1.0 means the spread of the
predicted probabilities is too wide, and a negative intercept means the probabilities sit too
high on average (the mean predicted probability exceeds the observed rate in both later
splits -- see section 5.1). The effect is mild and was **not** corrected: no calibration
post-processing was applied, by design. If calibrated probabilities matter for the downstream
scenario engine, that is a separate, later step.

## 7. Warnings and limitations

1. **Synthetic data.** These metrics measure how well a logistic model recovers a *simulated*
   funnel whose parameters are known to the generator. They are not institutional performance
   and carry no external validity.
2. **Selection bias in the population.** The modelling view is filtered to
   `stage_reached_order >= 3`, which conditions on latent intent and acquisition channel
   (the channel mix differs from `fact_application` by up to 2.41 percentage points). The
   model answers *"of those who submit, who will enrol"*, not *"which prospects should we
   push harder"*. A top-of-funnel propensity model is a different, undefined task.
3. **Base rate differs by split.** Enrolment rate falls monotonically across cycles
   (0.2923 train -> 0.2661 validation -> 0.2629 test). The model is penalised on the two later
   cycles for a drift it cannot observe at training time.
4. **Unseen categorical levels at test time.** `cycle_id = CYC-2025` and its campaign levels
   never appear in training. `OneHotEncoder(handle_unknown="ignore")` maps them to an
   all-zero block, so the model must fall back on the shared features. This is a genuine
   forward-deployment property of a real chronological split, not an artefact.
5. **Absolute-time features do not extrapolate.** The four declared date features are
   encoded as days since a fixed anchor, so the model can learn an absolute calendar
   position. Because the test cycle is two years after the earliest training cycle, this
   encoding cannot be verified on unseen time and is a plausible source of test-set
   degradation. The contract already provides `week_of_cycle_at_submission` and
   `month_of_submission` as cycle-relative alternatives.
6. **Two training cycles only.** The split is 2/1/1 by design (contract E.5), which is thin
   for a model with this many inputs and no cross-validation.
7. **Rows are not independent.** 2,529 applicants hold more than one application (maximum 3).
   `split_hint` is cycle-based, so an applicant with applications in two cycles can appear in
   both train and test. Any resampling, bootstrapping or significance testing **must** group
   by `applicant_id`. No resampling was performed in this baseline, so the reported figures
   are not affected by this.
8. **Seat capacity is a planning attribute, not an admission cap.** `base_seat_capacity` is
   included because it is a declared feature, but actual admits exceed the declared capacity
   by roughly 4.7x in the generated data. It must not be read as a hard cap or as
   "seats filled".
9. **Attribution fields are associational.** `acquisition_channel`, `acquisition_source`,
   `campaign_id` and `is_referral_alumni` are first-touch records. Any apparent channel
   effect is confounded by applicant mix. No causal or uplift claim is licensed by this
   dataset, and the coefficients in section 5.4 must not be read causally.
10. **This is a baseline, not a tuned model.** No hyper-parameter search, no cross-validation,
    no ensemble, no calibration post-processing and no threshold optimisation were done, by
    design. The numbers are a floor to beat, not a ceiling.
