# AdmitFlow - Forecast Results

> **The dataset is synthetic.** These are forecasts of a simulated admissions funnel
> generated by `scripts/generate_dataset.py`. They are **not** real-world forecast
> performance and must never be presented as such.

Target: `cum_enrolled` at forecast origin + H. Panel: `data/raw/fact_forecast_panel.csv`
(programme x cycle x ISO week). Origins: the 552 rows where `is_forecast_eligible = 1`.

---

## 1. Forecast design and feature construction

| Property | Value |
|---|---|
| Row unit | one forecast: (programme, cycle, origin week, horizon) |
| Target quantity | count of enrolled applications, cumulative from cycle start |
| Panel grain | `programme_id` x `cycle_id` x ISO week (2,064 rows) |
| Forecast origin `T` | eligible week, rolling weekly within the cycle |
| Horizon `H` | 1, 2, 4, 6 weeks |
| Target | `cum_enrolled` observed at week `T + H` (a real observed cell) |
| Eligibility | contract F conditions 1-4, pre-computed in `is_forecast_eligible` |
| Split | panel `split_hint` - CYC-2022+2023 train, CYC-2024 validation, CYC-2025 test |
| Feature rows | 2,208 = 552 origins x 4 horizons |
| Features | 53 (48 numeric, 5 categorical) |

**Why cumulative rather than weekly.** A weekly increment of `enrolled` is zero in most
weeks, which makes error metrics degenerate. Cumulative yield is monotone and is the
quantity stakeholders actually ask for ("how many enrolled by 15 February?"). This
is the contract's decision D-09, not a modelling preference made here.

**Split.** The existing chronological `split_hint` from the panel is used unchanged, as
contract E.5 requires. No new split was invented. Note this is a *target-cycle holdout*
rather than a rolling-origin backtest - contract T-05 flags that choice as still open
for the project owner, and it is not resolved here.

### Features, all from panel history at or before T

Every feature is produced by `origin_features()` in
`scripts/build_forecast_features.py`, which receives a frame **already sliced to**
`week_index_in_cycle <= T`. Trailing rolling windows end at the origin.

| Group | Features |
|---|---|
| Funnel levels at T | `cum_applications_opened`, `cum_applications_started`, `cum_applications_submitted`, `cum_applications_verified`, `cum_decisions_issued`, `cum_admitted`, `cum_enrolled` |
| Weekly flows at T | `wk_applications_submitted`, `wk_applications_verified`, `wk_decisions_issued`, `wk_admitted`, `wk_enrolled` |
| Cumulative rates at T | `cum_submit_to_verify_rate`, `cum_admit_rate`, `cum_enrolment_yield` |
| Enrolment lags | `lag_cum_enrolled_{1,2,4}`, `lag_wk_enrolled_{1,2,3,4}` |
| Trailing means / spread | `roll{4,8,12}_wk_enrolled_mean`, `roll{4,8}_wk_enrolled_std`, `roll{4,8}_wk_submitted_mean`, `roll4_wk_decisions_mean`, `roll4_wk_admitted_mean` |
| Momentum | `enrol_delta_1`, `enrol_delta_4`, `enrol_acceleration` |
| Funnel progress | `weeks_since_first_decision`, `weeks_since_first_enrolment`, `has_decisions`, `has_enrolments` |
| Programme attributes | `duration_years`, `annual_fee_inr`, `base_seat_capacity`, `review_duration_days`, `demand_weight`, `selectivity_tier`, `campus_region_id`, `award_level`, `faculty`, `programme_id` |
| Cycle attributes | `total_weeks`, `cycle_year_offset` |
| Horizon | `horizon_weeks` (so ONE model serves all four horizons) |

**Deliberately excluded as post-origin:**

| Column | Why excluded |
|---|---|
| `n_applications` | **The main trap.** It is the programme-cycle total application count, verified constant within every one of the 48 programme-cycles. It is only knowable at cycle end, so using it as a feature is pure look-ahead. |
| `is_forecast_eligible` | Origin-selection flag, not a quantity. |
| `panel_id` | Row key. |

Contract E.3 states features are "the panel history strictly up to and including week
T". The `cum_*` value **at** week T is therefore treated as known at the origin, as the
contract specifies. If an institution instead treats the origin as the *start* of week
T, every `cum_*` feature would need a one-week lag; that is a contract interpretation
question, not something this script decides.

## 2. Leakage guard

`run_leakage_guard()` in `scripts/build_forecast_features.py` is mandatory, executable,
and run by both scripts. It performs three checks:

| Check | What it does | Result |
|---|---|---|
| Allow-list | Asserts no excluded/post-origin column is in the feature matrix | **pass** |
| Target integrity | Asserts every target is the real observed `cum_enrolled` at `T + H` for 2,208 rows | **pass** |
| Future-corruption invariance | Rebuilds **all 552 origins** from a panel whose every value in weeks `> T` is overwritten by a sentinel, and asserts identical features (105,984 cells compared) | **pass** |

The third check is the real proof rather than an assertion of intent. A feature derived
from any week after the origin cannot survive its panel being overwritten.

**The guard is itself tested.** `--self-test` injects a deliberate look-ahead (a builder
that forgets to slice, reading the final `cum_enrolled` of the whole cycle) and confirms
the guard rejects it:

```
python scripts/build_forecast_features.py --self-test
[self-test] PASS  guard rejected the injected look-ahead: feature
           'cum_applications_opened' ... changed when post-origin panel values were
           corrupted: 959.0 -> 987654321.0
```

A guard never observed to fail is not evidence of safety, so this is part of the
deliverable. `train_forecast.py` rebuilds and re-guards before fitting and exits 4 rather
than train on unverified features.

## 3. Model

| Item | Value |
|---|---|
| Estimator | `RandomForestRegressor` |
| Configuration | `n_estimators=300, max_depth=12, min_samples_leaf=5, max_features=0.5, n_jobs=-1, random_state=20240817` |
| Preprocessing | numeric median impute; categorical most-frequent impute + one-hot |
| Scaling | none - trees are scale-invariant |
| Training rows | 1,152 (cycles 2022-2023) |
| Hyper-parameter search | **none** |
| Cross-validation | **none** |
| Seed | `20240817` |
| scikit-learn / numpy / pandas | `1.7.2` / `2.2.6` / `2.3.3` |
| Python / platform | `3.10.11` / `Windows AMD64` |

**One model, four horizons.** `horizon_weeks` is a feature rather than fitting four
separate models, so every horizon shares the same 1,152 training rows. The reported
metrics are computed per horizon regardless.

**Reference: persistence.** `predict cum_enrolled(T)`, i.e. assume no further
enrolment. For a cumulative target this is the reference that makes MAE interpretable -
a model that simply repeats today's total already scores well when weekly growth is
small, so a raw MAE on its own says little. Skill is reported as
`1 - MAE_model / MAE_persistence`.

**On the bias pattern.** Test bias alternates rather than growing with horizon (+3.29, +0.22, +2.21, +0.36 at H = 1, 2, 4, 6). The model is trained on four *discrete*
horizon values and cannot interpolate between them, so it snaps to the maturity
pattern it saw in training rather than tracking a smooth curve - and the yield curve
is strongly non-linear over this window, rising in every one of the 48 programme-cycles.
With 132 test points per horizon this could equally be sampling noise. No
cross-validation was run, so the two cannot be separated here, and no attempt was made
to correct the bias.

**On R2.** The pooled R2 above is dominated by the spread *between* programmes: a large
programme heading for 200 enrolments and a small one for 10 makes R2 look strong even
for a mediocre model. The `within-programme` column removes each programme's own mean
first, so it measures whether the model tracks a programme's deviation from its typical
level. That is the more honest number here, and the skill-versus-persistence figures are
the most interpretable of all.

## 6. Limitations

1. **Synthetic data.** Every figure describes a fit to a simulated funnel. Nothing
   transfers to real admissions forecasting.
2. **No tuning and no cross-validation.** One configuration, one fit, as instructed.
   These numbers are a defensible baseline, not a tuned ceiling.
3. **One held-out cycle per split.** Validation and test are each a single cycle, so
   the estimates carry sampling noise that a rolling-origin backtest would quantify.
   Contract T-05 records the holdout-versus-backtest choice as an open owner decision.
4. **Small sample.** 1,152 training rows and 132 test rows per horizon. A 300-tree
   forest on 132 test points cannot resolve small differences.
5. **The target is cumulative and near-deterministic given the origin.** Much of the
   signal is mechanical continuation of an existing yield curve, which is why the
   persistence reference is strong and why high pooled R2 must not be over-read.
6. **Origin convention.** Features include the panel values at week T itself, per
   contract E.3. An institution treating T as the start of the week would need a
   one-week lag on every cumulative feature.
7. **No prediction intervals.** Only point forecasts. An operational yield plan needs
   uncertainty, and none is produced here.
8. **Classification models untouched.** The Logistic Regression and Random Forest
   classification artifacts are unmodified by this step.
